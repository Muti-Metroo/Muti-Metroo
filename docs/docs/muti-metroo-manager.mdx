# Muti Metroo Manager

<div style={{ textAlign: "center", marginBottom: "2rem" }}>
  <img
    src="/img/mole-presenting.png"
    alt="Mole presenting dashboard"
    style={{ maxWidth: "180px" }}

Muti Metroo Manager is a single binary that serves a browser UI for a Muti Metroo mesh. It connects to the HTTP API of one agent and reverse-proxies the browser's requests to it, so everything that agent can see or reach through the mesh is available in the UI: the topology, routes, port forwards, mesh hostnames, remote shells, file transfer, ping, and sleep mode.

![Topology tab showing a four-agent mesh: gateway connected to transit and exit-cloud, and transit connected to exit-datacenter](/img/screenshots/muti-metroo-manager/01-topology.png)

```mermaid
flowchart LR
    Browser[Browser] -->|HTTP| Manager[Muti Metroo Manager<br/>:3000]
    Manager -->|HTTP API| Agent[Muti Metroo agent<br/>:8080]
    Agent -->|Mesh| Mesh[Other agents]
```

The React frontend is embedded in the binary; no web server or Node.js runtime is needed. The Manager keeps its own small SQLite database for UI state (settings, agent notes and icons, network names, station positions).

:::warning[Protect the Manager]
Anyone who can use the Manager acts with the permissions of the agent it connects to, including remote shells and file transfer across the mesh. Without an [access token](#access-token) it has no login, so it refuses a non-loopback listen address unless you pass `-insecure-no-auth`. Bind it to `127.0.0.1:3000`, or set an access token, on any host reachable from a network you do not trust.
:::

## Quick start

1. Make sure the agent has its HTTP API enabled (see [Agent requirements](#agent-requirements)).
2. Download and start the Manager on a host that can reach the agent's API:

   ```bash
   curl -L -o muti-metroo-manager https://github.com/Muti-Metroo/Muti-Metroo-Manager/releases/latest/download/metroo-manager-linux-amd64
   chmod +x muti-metroo-manager
   ./muti-metroo-manager -addr 127.0.0.1:3000 -agent http://127.0.0.1:8080
   ```

3. Open `http://localhost:3000` in a browser.

The startup log lists the listen address, the agent URL and whether the agent answered, whether a token is set, and the data directory. If the agent is unreachable, the Manager still starts and keeps probing it.

## Agent requirements

The Manager uses the agent's dashboard (`/api/*`) and remote (`/agents/*`) endpoints. Both are on by default when the HTTP API is enabled:

```yaml
http:
  enabled: true
  address: "127.0.0.1:8080"
  dashboard: true
  remote_api: true
```

Some operations need more than read access. They are greyed out or read-only in the UI when not available:

| Operation                                                           | Requirement                                                                                     |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Add, edit, or remove routes, peers, listeners, forwards, hostnames; rename agents | The connected agent holds `management.signing_private_key` ([Management keys](/configuration/management)) |
| Shell                                                               | The same signing key, plus shell enabled on the target agent ([Shell](/configuration/shell))    |
| Files                                                               | The same signing key, plus file transfer enabled on the target agent ([File Transfer](/configuration/file-transfer)) |
| Ping                                                                | ICMP enabled on the target agent ([ICMP](/configuration/icmp)); not offered for Windows agents  |
| Suspend and resume the mesh                                         | Sleep mode enabled on the connected agent ([Sleep](/configuration/sleep))                       |

### Bearer token

If the agent has `http.token_hash` set, the Manager needs the matching token. Give it to the Manager in one of these ways (highest precedence first):

1. `-agent-token-file <path>`: a file with the token on one line. Preferred for systemd and Kubernetes secrets.
2. `-agent-token <token>`: visible to other users through the process list; avoid in production.
3. The `METROO_MANAGER_AGENT_TOKEN` environment variable. The older `MUTI_METROO_TOKEN` still works but logs a deprecation warning.

```bash
./muti-metroo-manager -agent http://192.168.1.10:8080 \
  -agent-token-file /etc/muti-metroo-manager/token
```

When the Manager has no agent token and the agent answers `401`, the browser shows an **Authentication required** dialog instead. The token entered there is kept in the browser's session storage, or in local storage for 8 hours when **Remember on this device for 8 hours** is ticked. **Sign out** in the actions menu clears it. A token configured on the Manager always replaces a token sent by the browser.

### Access token

The Manager can require its own token for every `/api/*` route, including the proxied agent API that carries shells and file transfer. Set it with `-auth-token-file` (preferred), `-auth-token`, or the `METROO_MANAGER_AUTH_TOKEN` environment variable:

```bash
openssl rand -hex 32 > /etc/muti-metroo-manager/auth-token
./muti-metroo-manager -addr :3000 -agent http://192.168.1.10:8080 \
  -auth-token-file /etc/muti-metroo-manager/auth-token
```

Browsers then see a login screen; the token is exchanged for an `HttpOnly`, `SameSite=Strict` session cookie, marked `Secure` when the request arrives over HTTPS (including `X-Forwarded-Proto: https` from a reverse proxy). Scripts send `Authorization: Bearer <token>`.

Without an access token the Manager logs a warning at startup and refuses to listen on a non-loopback address unless `-insecure-no-auth` is set. [File shares](#file-shares) are not covered by this token; each share has its own user name and password.

## Using the web UI

### Layout

- **Header**: the connected agent's name and short ID, the main tabs, the actions menu (the vertical dots button), and a light/dark theme toggle. The theme follows the operating system preference until you change it and is remembered per browser.
- **Main tabs**: **Topology**, **Routes**, **Port Forwarding**, and **DNS**.
- **Actions menu**: **Mesh connectivity test**, **File shares...**, **Generate Muti Metroo agent config...**, **Generate Mutiauk config...**, **Settings...**, **Suspend mesh** or **Resume mesh** (when sleep mode is enabled), and **Sign out** (when the browser holds a token).
- **Footer**: the most recent topology event, the [mesh health](#mesh-test) summary, and the Manager version.

![Actions menu open on the Topology tab, listing Mesh connectivity test, Generate Muti Metroo agent config, Generate Mutiauk config, Settings, and Suspend mesh](/img/screenshots/muti-metroo-manager/22-actions-menu.png)

![Topology tab in the dark theme](/img/screenshots/muti-metroo-manager/25-topology-dark.png)

Destructive actions (removing routes, peers, listeners, forwards, hostnames, suffixes, and files) ask for confirmation.

### Topology

The **Topology** tab draws every agent as a station and every peer connection as a line between them. Click a station to open its [agent panel](#agent-panel). Hover a station or a connection for details, including the agent's notes.

- **Zoom** with the mouse wheel, toward the cursor, from 0.25x to 5x. A short scroll still scrolls the page; zooming starts after a longer wheel movement.
- **Pan** by dragging empty space.
- **Move a station** by dragging it. Stations snap to a grid; hold Alt (Option on macOS) to place freely. Station positions are saved in the Manager database, so everyone using the same Manager sees the same layout. Pan and zoom are saved per browser.
- **Reset view** (top left) appears when the view or any station has been moved, and restores the default layout.
- **Fullscreen** toggle (bottom left).

Connection lines are colored by round-trip time (under 50 ms, under 200 ms, slower) and marked when a peer is unresponsive. Lines that carry traffic are animated from the dialing side to the listening side. Joins, departures, link changes, route changes, and mesh test changes appear as events in the footer. Optional sound effects accompany peer joins and departures, mesh test results, and station clicks; turn them off in [Settings](#settings) or for all users with `-no-sounds`. Animations and sounds are off when the operating system requests reduced motion.

#### Search

Press `/` (from any tab) or click the search icon to search agents. Search matches the agent ID, IP addresses, role, display name, hostname, exit routes, domain routes, forward keys, SOCKS5 address, and notes, and shows which field matched. Use the arrow keys and Enter to open a result.

![Topology search for "a" listing gateway, transit, and exit-datacenter with their short IDs](/img/screenshots/muti-metroo-manager/02-topology-search.png)

#### Networks

Agents can be grouped into named boxes on the map. Set the **Networks** field on an agent's Info tab to a comma-separated list (for example `prod,edge-1`); agents that share a network are drawn inside the same box. Click a box label to rename it. Boxes can be nested and moved.

![Topology tab with transit and exit-datacenter inside a datacenter network box and exit-cloud inside a cloud network box](/img/screenshots/muti-metroo-manager/21-topology-networks.png)

### Agent panel

Clicking a station opens a side panel for that agent. The pencil button next to the name renames the agent (sets its display name). The panel has these tabs:

#### Info

Agent ID, hostname, platform, version, uptime, PID, IP addresses, which capabilities are enabled (shell, file transfer, signing key), SOCKS5 address, and advertised routes. Below them are three fields stored in the Manager database:

- **Notes**: free text, saved when the field loses focus, on Ctrl+S or Cmd+S, and when the panel closes.
- **Map icon**: an icon drawn on the station. **Choose...** opens a picker with operating system, network, compute, storage, industrial, and other device icons.
- **Networks**: see [Networks](#networks).

![Info tab for gateway showing reachability, hostname, platform, version, IP address, SOCKS5 address, remote access status, map icon, networks, and notes](/img/screenshots/muti-metroo-manager/03-agent-info.png)

#### Routes

The agent's dynamic CIDR routes. Add a route (CIDR, metric, comment), remove one, or **Edit** one to change its comment, **Source IP**, and **Interface**. The Source IP and Interface fields suggest the agent's own addresses and network interfaces; a warning appears when the chosen source address belongs to a different interface. The meaning of each field is described in [route](/cli/route).

![Routes tab for exit-cloud listing its 0.0.0.0/0 and 172.31.0.0/16 routes with comments and metrics](/img/screenshots/muti-metroo-manager/05-agent-routes.png)

![Edit route dialog for 10.20.0.0/16 on exit-datacenter with comment, Source IP, and Interface fields filled in](/img/screenshots/muti-metroo-manager/20-route-edit-dialog.png)

#### Forwards

Two sub-tabs: **Listeners (ingress)** for forward listeners (key and address) and **Endpoints (exit)** for forward endpoints (key and target). A usage hint shows a ready-to-run `curl` command for the first listener, including a `--resolve` variant for TLS services that need the right SNI name. Endpoints registered by [Mutiauk expose](/mutiauk#expose-publishing-local-services) are marked as such.

![Forwards tab for transit showing the tools-share listener on port 8090 and the curl usage hint](/img/screenshots/muti-metroo-manager/06-agent-forwards.png)

#### Connectivity

Two sub-tabs:

- **Peers**: the agent's peer connections. Add a peer by address, transport, path (for `h2` and `ws`), and optional keepalive; the Manager probes the address first and offers **Add anyway** if the probe fails. Runtime peers can be removed.
- **Listeners**: transport listeners. Add one by transport (`quic`, `h2`, `ws`), bind address (for example `:4433`), path (`h2` and `ws`), optional advertise address (`host:port`, published to the mesh as a dial target), and the `plaintext` option for `ws` behind a TLS-terminating proxy. Listeners from the agent's config file are marked `static` and cannot be removed here.

Without a management signing key on the connected agent, both sub-tabs are read-only. See [peer](/cli/peer) and [listener](/cli/listener) for what each field does.

![Peers sub-tab for gateway listing inbound peers transit over QUIC and exit-cloud over WebSocket](/img/screenshots/muti-metroo-manager/04-agent-peers.png)

![Listeners sub-tab for gateway listing its static QUIC listener on port 4433 and WebSocket listener on port 8443 with their advertise addresses](/img/screenshots/muti-metroo-manager/19-agent-listeners.png)

#### Shell

An interactive terminal on the agent. Pick a shell from the list to start a session. **Reconnect** appears when the session ends or fails, and **Copy CLI** copies the equivalent `muti-metroo shell` command.

![Shell tab with a bash session on exit-datacenter showing the output of uname and ls](/img/screenshots/muti-metroo-manager/10-agent-shell.png)

#### Files

A file browser limited to the agent's allowed paths. The toolbar has **Up**, **Path**, **Upload**, and **Refresh**. **Path** (or clicking the leading `/` in the breadcrumb on Unix agents) opens a field to type a path; `~` expands to the agent user's home directory. Drop files or folders onto the list to upload them; folders upload recursively. Each entry has a menu to view (text, hex, image, or PDF), download (folders as `.tar.gz`), change permissions, or delete.

![Files tab for exit-datacenter listing the configs and reports folders in /srv/files](/img/screenshots/muti-metroo-manager/11-agent-files.png)

#### Ping

Sends ICMP echo requests from the agent to an IP address: 10, 25, or 50 requests, or continuously, one per second. The table shows each sequence number, round-trip time, and result, with minimum, average, and maximum RTT, loss, and the source and destination addresses the exit used.

## File shares

Muti Metroo Manager can share a folder on any agent as a network drive. You pick an agent and a folder in the file browser, and Manager serves that folder over WebDAV from the Manager host. Users mount it with the WebDAV client built into their operating system: Finder on macOS, Explorer or `net use` on Windows, and GNOME Files, davfs2 or rclone on Linux.

Manager does not copy the folder. Every WebDAV request becomes a call to the connected agent's file transfer API (`file/browse`, `file/download`, `file/upload`). The connected agent signs each operation with the management key and relays it through the mesh to the target agent. A share can therefore reach only what the target agent's `file_transfer.allowed_paths` allows, exactly like the Files tab.

### Requirements

On the target agent (the one that holds the folder):

- `file_transfer.enabled: true`
- The shared folder inside `file_transfer.allowed_paths`. Glob roots work; the share root must itself be an existing directory.
- `management.signing_public_key` set, so it accepts signed file operations.
- Muti Metroo 4.12.0 or later, on this agent and on the agent Manager connects to. Earlier versions sign file operations differently (see [Mixed versions](/security/authentication#how-a-request-is-signed)) and lack the `mkdir`, `rename`, and ranged download operations a share needs.

On the agent Manager connects to (`-agent`):

- `management.signing_private_key` set, so it can sign operations on Manager's behalf.
- If its HTTP API requires a bearer token, give the token to Manager with `-agent-token-file` (or `METROO_MANAGER_AGENT_TOKEN`). The WebDAV gateway runs inside Manager and cannot use a token that was only pasted into the browser.

On the Manager host:

- Clients must be able to reach Manager's listener (`-addr`). A loopback bind such as `127.0.0.1:3000` allows mounts from the Manager host only.
- Writes are buffered in the host's temp directory until the client closes the file, so it needs free space for the largest file you expect to upload.

### Creating a share

1. Open an agent, go to the **Files** tab and navigate to the folder.
2. Click **Share**.
3. Choose a share name. It becomes part of the URL (`/dav/<name>/`), so it is limited to lower-case letters, digits, `-` and `_`.
4. Leave **Read-only** checked unless clients need to change files. Read-write lets anyone with the password create, overwrite, rename and delete files in the folder.
5. Optionally set a user name (defaults to the share name) and a password (8 to 72 characters). Leave the password empty to have Manager generate one.
6. Click **Create share**. Manager checks that the folder exists on the agent and is a directory, then shows the mount URL, the user name, the password and mount instructions for each operating system.

The generated password is shown once. Manager stores only a bcrypt hash; if the password is lost, rotate it.

### Managing shares

Open **Actions > File shares** to see every share with its status, agent, folder, access mode and mount URL. From there you can:

- **Disable / Enable** a share. A disabled share answers 404 and keeps its settings.
- Switch between **read-only** and **read-write**.
- **Rotate password**. The new password is shown once; the old one stops working immediately, including for clients that are already mounted.
- **Delete** the share. Files on the agent are not touched.
- Open **Mount help** for the per-OS instructions.

Shares are stored in Manager's SQLite database and survive restarts.

### Mounting

The mount URL is `http://<manager-host>:<port>/dav/<name>/` (or `https://` behind a TLS proxy). Use the host name or address the clients use to reach Manager.

#### macOS

In Finder choose **Go > Connect to Server** (Cmd+K), enter the mount URL and sign in with the share's user name and password. The share appears under `/Volumes`. A read-only share mounts read-only.

#### Windows

The **WebClient** service must be running (`sc start WebClient`; set it to Automatic to keep it across reboots). Then run:

```bash
net use Z: http://manager.example:3000/dav/docs/ /user:docs *
```

The `*` prompts for the password. **Map network drive** in File Explorer accepts the same URL.

Two Windows defaults get in the way:

- Windows refuses HTTP Basic authentication over plain HTTP. Either use HTTPS, or set `BasicAuthLevel` to `2` (DWORD) under `HKLM\SYSTEM\CurrentControlSet\Services\WebClient\Parameters` and restart the WebClient service.
- Windows limits WebDAV file transfers to 50 MB. Raise `FileSizeLimitInBytes` (DWORD, up to `4294967295`) in the same key and restart WebClient.

#### Linux

GNOME Files: open **Other Locations**, enter `dav://manager.example:3000/dav/docs/` (`davs://` for HTTPS) in **Connect to Server**. From a terminal:

```bash
gio mount 'dav://docs@manager.example:3000/dav/docs/'
```

davfs2:

```bash
sudo mkdir -p /mnt/docs
sudo mount -t davfs 'http://manager.example:3000/dav/docs/' /mnt/docs
```

rclone (no root needed; the mount point must exist):

```bash
rclone mount :webdav: ~/docs \
  --webdav-url 'http://manager.example:3000/dav/docs/' \
  --webdav-user docs \
  --webdav-pass "$(rclone obscure 'PASSWORD')" \
  --vfs-cache-mode writes
```

### Security

- `/dav/` is not covered by Manager's own access token, because operating system WebDAV clients can only send a user name and password. Each share has its own credentials instead, and every request to `/dav/<name>/` must carry them. The Manager token does not open a share, and share credentials do not open the Manager API.
- After 10 failed logins within 5 minutes from one client address, Manager refuses further requests from that address with HTTP 429 until the 5 minutes are over. Behind a reverse proxy all clients share the proxy's address, so a client with a wrong saved password can briefly lock out everyone.
- Manager has no TLS listener of its own. Over plain HTTP the share password and the file contents cross the network unencrypted. For anything beyond a trusted network, put Manager behind a TLS-terminating reverse proxy and mount the `https://` URL.
- Shares are read-only by default, and a read-only share refuses every changing request (upload, delete, create folder, copy, move, lock) before it reaches the agent.
- Share paths are confined to the shared folder: `..` segments, backslashes, and (for Windows agents) drive letters in names are rejected. The agent still enforces `allowed_paths`, also after resolving symbolic links, so a link inside the folder that points outside the allowed paths cannot be opened through the share.
- Files are served from Manager's origin with a `Content-Security-Policy: sandbox` header, so an HTML or SVG file on an agent cannot run script against the Manager UI when opened in a browser.
- Create, update and delete of shares are written to Manager's log as audit events. Failed share logins are logged with the client address.

### Limitations

- Every operation is a round trip through the mesh, so listing large folders and opening many small files is slower than a local file server. File metadata is cached for 2 seconds.
- Reads are fetched in ranges with a read-ahead of 1 to 4 MiB, so previews and seeks do not download whole files. Writes are buffered on the Manager host and uploaded when the client closes the file; large uploads are limited by `file_transfer.max_file_size` on the target agent and by the 30 minute upload timeout.
- Locks (needed by Finder and Office to write) are kept in Manager's memory and are lost when Manager restarts. Only exclusive write locks are supported; a client that asks for a shared lock gets "not implemented".
- Custom WebDAV properties are not stored; clients that set them (for example Windows timestamps) get a "forbidden" result for those properties, which they ignore.
- `PROPFIND` with `Depth: infinity` is refused.
- New files are created with the agent's default upload mode (`0600`); overwritten files keep their existing mode.
- macOS metadata (`._*` AppleDouble files, `.DS_Store`, `.Spotlight-V100`, `.Trashes`, `.fseventsd`, `.TemporaryItems`) is never written to the agent. Manager keeps it in memory, so Finder and `cp` work as usual, and drops it when Manager restarts: extended attributes and Finder view settings of files copied from a Mac are not stored on the target. Such files already present in the folder are hidden from the share.

## Command-line reference

```text
muti-metroo-manager [run] [flags]          start the HTTP server (default)
muti-metroo-manager check [flags]          validate config + probe agent, exit 0/1
muti-metroo-manager config show [flags]    print resolved config with provenance
muti-metroo-manager config init [path]     emit a commented TOML config template
muti-metroo-manager version | -V           print version and build info
```

- `check` validates the configuration and the data directory and calls the agent's `/healthz`. It exits 0 when all pass and 1 otherwise, without starting the listener.
- `config show` prints every setting with its source (`default`, `file`, `env`, `flag`, or `token-file`).
- `config init` writes a commented TOML file with every key; `-force` overwrites an existing file.

### Flags

These flags apply to `run`, `check`, and `config show`. Flags use a single dash.

| Flag                | Default                  | Description                                                                                         |
| ------------------- | ------------------------ | --------------------------------------------------------------------------------------------------- |
| `-config`           |                          | TOML config file                                                                                    |
| `-addr`             | `:3000`                  | Listen address for the UI. The default binds every interface.                                      |
| `-agent`            | `http://127.0.0.1:8080`  | Agent HTTP API URL (`scheme://host:port[/prefix]`)                                                  |
| `-agent-token`      |                          | Bearer token for the agent                                                                          |
| `-agent-token-file` |                          | File containing the bearer token                                                                    |
| `-agent-ca-bundle`  |                          | PEM file with extra CA certificates for verifying an `https://` agent                               |
| `-insecure-skip-verify` | `false`              | Do not verify the agent's TLS certificate. The agent token can then be intercepted.                 |
| `-auth-token`       |                          | The Manager's own [access token](#access-token)                                                     |
| `-auth-token-file`  |                          | File containing the access token                                                                    |
| `-insecure-no-auth` | `false`                  | Allow a non-loopback `-addr` without an access token                                                |
| `-data-dir`         | see [Data directory](#data-directory) | Directory for the database and the instance lock                                       |
| `-log-level`        | `info`                   | `debug`, `info`, `warn`, or `error`                                                                 |
| `-log-format`       | `text`                   | `text` or `json`                                                                                    |
| `-metrics-addr`     |                          | Listen address for the [metrics](#metrics) endpoint; empty disables it                              |
| `-no-sounds`        | `false`                  | Turn UI sound effects off for all users                                                             |

### Config file

Settings are resolved in this order, later ones winning: built-in defaults, the TOML file given with `-config`, environment variables, flags. Each flag has a TOML key with underscores instead of dashes:

```toml
addr = "127.0.0.1:3000"
agent = "http://127.0.0.1:8080"
agent_token_file = "/etc/muti-metroo-manager/token"
auth_token_file = "/etc/muti-metroo-manager/auth-token"
data_dir = "/var/lib/muti-metroo-manager"
log_level = "info"
log_format = "json"
metrics_addr = ""
no_sounds = false
```

The tokens themselves cannot be set in the TOML file; use `agent_token_file` and `auth_token_file`.

### Environment variables

| Variable                     | Description                                     |
| ---------------------------- | ----------------------------------------------- |
| `METROO_MANAGER_AGENT_TOKEN` | Bearer token for the agent                      |
| `METROO_MANAGER_AUTH_TOKEN`  | The Manager's own access token                  |
| `MUTI_METROO_TOKEN`          | Deprecated name for the same; logs a warning    |

### Data directory

The data directory holds `muti-metroo-manager.db` (the SQLite database) and `muti-metroo-manager.lock`. Back up the database with your config. Defaults:

| Platform            | Default                                              |
| ------------------- | ---------------------------------------------------- |
| macOS               | `~/Library/Application Support/Muti-Metroo-Manager`  |
| Linux, as root      | `/var/lib/muti-metroo-manager`                       |
| Linux, other users  | `$XDG_CONFIG_HOME/muti-metroo-manager` (`~/.config/muti-metroo-manager`) |
| Windows             | `%AppData%\muti-metroo-manager`                      |

Only one Manager can use a data directory at a time. A second instance pointed at the same directory exits with `another muti-metroo-manager instance is already running`. Give each instance its own `-data-dir`.

## Operations

### Health check

`GET /healthz` on the main listener returns the Manager's status and the result of its last probe of the agent. It always answers `200`; check `agent_reachable` in the body.

```bash
curl http://localhost:3000/healthz
```

```json
{"status":"ok","version":"0.2.39","agent_reachable":true,"agent_status":200,"agent_latency_ms":2,"agent_checked_ago_s":4}
```

### Metrics

With `-metrics-addr` set, a separate listener serves Prometheus text format at `/metrics`: `metroo_manager_requests_total` and `metroo_manager_request_duration_seconds` (by method, route, and status) and `metroo_manager_agent_reachable`. Bind it to a private address.

```bash
./muti-metroo-manager -addr 127.0.0.1:3000 -metrics-addr 127.0.0.1:9101
curl http://127.0.0.1:9101/metrics
```

### Logs

Logs go to standard error, as text or (with `-log-format json`) one JSON object per line. Every request is logged with method, path, status, latency, client address, and a request ID. The ID is taken from the client's `X-Request-ID` header (which is also passed on to the agent) or generated, and is returned in the response. Changes to the Manager's own state (settings, agent notes and icons, network names, station positions) also produce a log line with `audit=true`. Operations performed on the agent appear in the request log.

### Running as a service

The Manager repository has a systemd unit (`contrib/systemd/muti-metroo-manager.service`) and a launchd plist (`contrib/launchd/`). The systemd unit runs as a dedicated user, validates with `check` before each start, and reads `/etc/muti-metroo-manager/config.toml`:

```bash
sudo useradd --system --no-create-home muti-metroo-manager
sudo install -m 755 muti-metroo-manager /usr/local/bin/muti-metroo-manager
sudo install -d -m 750 -o muti-metroo-manager -g muti-metroo-manager \
  /var/lib/muti-metroo-manager /etc/muti-metroo-manager
sudo /usr/local/bin/muti-metroo-manager config init /etc/muti-metroo-manager/config.toml
sudo cp muti-metroo-manager.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now muti-metroo-manager
```

Edit `config.toml` before starting, at least `addr`, `agent`, and `agent_token_file`.
